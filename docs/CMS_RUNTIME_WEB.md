# CMS runtime delivery (Episode 3)

The public `cms-public` function is the Web content source. On each uncached server render, Astro middleware requests `GET /functions/v1/cms-public/site?locale=en|es|fr`, validates `cms-site-v1`, and maps that one response to a request-scoped publication model. Home, service and event details, gallery, Tree, navigation, footer, and SEO use the same generation. CMS content is rendered into HTML on the server; browser code does not fetch CMS content. Dynamic detail/category routes return 404 when absent from CURRENT. If the API is unavailable or invalid, uncached page requests return 503 without fixture or historical publication fallback.

Set `CMS_PUBLIC_API_ORIGIN` to the public Supabase API **origin** (for example, `https://project.supabase.co`) in each Web runtime environment. This is public configuration, not a credential. No service role key, publishable key, GitHub token, or Vercel CMS token is used for public CMS reads. Locally, point it at a running local `cms-public` API, for example `http://127.0.0.1:54321`. HTTP is accepted only for localhost. A Web production build does not need this value because CMS pages render on request. Normal tests use a deterministic localhost mock and never contact Supabase.

Astro 7 uses `@astrojs/vercel` with server output and 30-second ISR expiration. CMS pages, including pages with CMS-owned navigation/footer, render on demand. Technical `robots.txt`, assets, and the optional CMS-01 pilot remain prerenderable. The dynamic `cms-sitemap.xml` lists CURRENT slugs and all locale URLs; robots advertises it alongside the original static sitemap. Image paths from the DTO are resolved against `CMS_PUBLIC_API_ORIGIN` and rendered as responsive `<picture>` derivatives. The browser never receives private Storage keys.

Publishing CMS copy or images updates CURRENT through the API and does not require a Web build, Web deployment, cross-repository checkout, `CMS_PUBLICATION_INPUT`, a Web SHA match, Vercel Prepare, or Vercel Promotion. Web code changes still follow the normal Vercel Git deployment process. Vercel's ISR stale-while-revalidate behavior should serve an existing cached page during regeneration failures; cold requests receive the 503 response. This and the actual media front door require remote certification in Episode 5. The API already filters Tree events by server time; Web never reintroduces expired entries. At a 30-second ISR window, an already cached agenda can remain visible until regeneration.

The CMS-08D static materialization document records the former Web adapter. Its finalizer and build input are no longer in the production Web path. The old artifact hash helper remains only for its historical fixed-vector test.
