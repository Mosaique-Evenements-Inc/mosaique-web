# Mosaïque i18n Foundation

## Status

R1 defined the localization contract, R2 completed the translation inventory, and R3 migrated the
default locale to English. Service, Event, Site Shell, Gallery, Home, About, Quote/Contact, and Tree
Link now render EN-CA / ES / FR-CA through the same static architecture.

## Locales and URLs

| URL locale | Language tag | Public prefix |
| ---------- | ------------ | ------------- |
| `en`       | `en-CA`      | none          |
| `es`       | `es`         | `/es/`        |
| `fr`       | `fr-CA`      | `/fr/`        |

English is the default locale, so `/`, `/services/bodas`, and `/events/wedding-r-r` render English.
Spanish uses `/es/` and French uses `/fr/`, followed by the same locale-independent content paths.
Legacy `/en/*` URLs must receive a one-hop permanent hosting redirect to the equivalent unprefixed
English path; the static build does not emit client redirect pages.

`Locale` means the URL locale (`es`, `en`, or `fr`). `LanguageTag` means the document or SEO
language tag (`es`, `en-CA`, or `fr-CA`). `en-CA` and `fr-CA` are never URL prefixes.

## Architecture

Astro native i18n is configured in `astro.config.mjs` with the default locale unprefixed. The
framework helpers are wrapped by `src/core/i18n/routing/paths.ts`:

- `getLocaleFromUrl(url)` resolves the URL locale;
- `getLocalizedPath(path, locale)` delegates path generation to `astro:i18n`;
- `switchLocalePath(currentUrl, targetLocale)` preserves the current content path while changing
  locale.

Components use these helpers for internal localized links and must not concatenate prefixes
manually. The URL is the locale authority. The language switcher preserves content path, query,
and hash without browser-language detection, cookies, or locale storage.

## Translation Ownership

Each feature owns its dictionaries under `src/features/<feature>/i18n/`. There is no global
translation file. The shared contracts in `src/core/i18n/translation/` provide typed dictionary
shapes and a build-time-friendly translator. A feature dictionary should use a shared shape with
`LocaleDictionaries<T>` so missing keys fail TypeScript validation when dictionaries are added.

Current examples are `features/services/i18n`, `features/events/i18n`,
`features/gallery/i18n`, and `features/site-shell/i18n`. Their localized projections are applied at
the feature boundary; canonical records continue to own IDs, slugs, media, and relationships.

New user-facing text must be localized from its feature source. This includes headings, controls,
labels, placeholders, validation messages, ARIA labels, metadata, empty states, and visible errors.
Developer-only logs and diagnostics are excluded.

## Fallback Policy

The default strategy is explicit and conservative: English is the technical fallback locale, and development
throws when a requested key is absent rather than rendering a technical key. Production returns an
empty string for an unresolved key so internal identifiers never become visible user-facing copy;
missing translations must still be corrected in the owning feature before release.

Canonical Spanish source records, business values, IDs, and slugs remain Spanish where originally
approved; changing the technical fallback does not rewrite those values.

## Domain Data

Domain IDs, slugs, Event/Service relationships, categories, gallery records, and media contracts
remain locale-agnostic. Localized labels and descriptions are presentation content; they must not
change `ServiceId`, Event IDs, `EventCategoryId`, or routing slugs.

## Adding Content

To add a user-facing string, add its typed key to the owning feature contract, provide the key in
all required locale dictionaries, and consume it through the feature translator. Do not use locale
ternaries in components or hardcode a localized string in markup.

To add a feature, create its own `i18n/` folder and dictionary contract. To add a locale, update
the Astro config, core locale registry, language tag mapping, every feature dictionary contract,
localized route matrix, metadata alternates, and all validation commands before enabling it.

## SEO

`BaseLayout` emits localized `lang`, canonical, Open Graph, Twitter, JSON-LD, and reciprocal
`hreflang` links. `x-default` points to the unprefixed English equivalent. When `SITE_URL` exists,
the sitemap includes all three active locales and their alternates while excluding 404 pages.

## R2 Hardcoded Text Audit

The repository-wide audit classified remaining literals as follows:

- **Intentionally invariant proper nouns:** `MOSAÏQUE EVENTS`, `MOSAÏQUE ÉVÉNEMENTS`, collaborator
  names, event names such as `Wedding R&R`, and approved brand statements that are intentionally
  English in the Spanish experience.
- **Technical/internal:** route IDs, slugs, form field names and values, HTTP error identifiers,
  CSS/data attributes, ISO date formats, schema types, `es_CA`, and build/runtime messages.
- **Migrated:** Home editorial copy, service and event projections, Gallery labels, Site Shell
  navigation/footer labels, Quote/Contact labels and validation copy, calendar controls, carousel
  controls, ARIA labels, skip link, and route metadata defaults.

Canonical Spanish content modules remain the reviewed source records; active Home rendering uses
the typed feature-owned projections in `src/features/home/i18n/`. No unclassified active user-facing
literal remains in the audited UI paths.

## Performance and Validation

The URL is the source of truth. The i18n architecture adds no client locale runtime, React context,
Zustand state, browser-language detection, or locale persistence. Astro resolves locale
configuration and translations during build/render. Theme storage remains independent.

Validation runs `pnpm build`, `pnpm lint`, `pnpm test`, `pnpm typecheck`, `git diff --check`, and
scoped Prettier. The routing test covers the locale registry, representative static and dynamic
paths, language-switcher destinations, canonical metadata, alternates, `x-default`, legacy EN-page
absence, and the English general 404.

The general static 404 is English and keeps `noindex, nofollow`. `/es/404/` and `/fr/404/` remain
localized, non-indexable static pages but are not locale-specific error handlers. Tree Link shares
the routing migration at `/tree`, `/es/tree`, and `/fr/tree` while retaining its design, content,
theme storage, and interactions.
